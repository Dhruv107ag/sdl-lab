1. Crucial UML Diagram Comparisons (Frequently Asked by Examiners)

Examiner Focus: Why do we have multiple UML diagrams, and how do they differ?

Examiners routinely ask students to compare pairs of diagrams to test if they understand the distinction between analysis vs. design, static structure vs. dynamic behavior, and logical modules vs. physical deployable components.

DIFF 1 Analysis Class Diagram vs. Design Class Diagram (Assignment 6 Core Requirement)

Assignment Context: Task 1 explicitly warns: "Do not simply reproduce the analysis class diagram from Assignment 4. Refine it by adding implementation-oriented details while maintaining consistency."

Dimension Analysis Class Diagram (Assignment 4) Design Class Diagram (Assignment 6)
Objective Capture problem-domain vocabulary and business concepts without software bias. Specify the exact implementation blueprint for developers and database engineers.
Abstraction Level Conceptual / Domain level (BCE: Boundary, Control, Entity analysis stereotypes). Implementation / Code level (Controllers, Services, Repositories, Entities, DTOs).
Attributes Plain domain names (e.g., description, status); types are generic or omitted. Fully typed with language types (e.g., - description: string, - status: ComplaintStatus, - id: UUID).

Operations / Methods High-level responsibilities (e.g., verify(), notify()), no parameter types or return types. Complete method signatures with parameter lists, data types, return types, and exceptions (e.g., + assignStaff(staffId: int, sla: int): boolean).
Relationships Pure semantic associations (e.g., "Student files Complaint"). Directional navigability arrows, foreign key references, collection types (e.g., List<AuditLog>), aggregation, and composition diamonds.

DIFF 2 Collaboration (Communication) Diagram vs. Sequence Diagram

Both are UML Interaction Diagrams and are semantically isomorphic (you can convert one to the other without loss of information), but they emphasize completely different perspectives of object behavior.

Dimension Collaboration / Communication Diagram Sequence Diagram
Primary Emphasis Spatial Organization & Object Links: Emphasizes structural topology and which objects talk to which objects. Chronological Time Sequence: Emphasizes the exact order and timing of messages along vertical lifelines.
Visual Layout Graph network layout: Objects are rectangles connected by association lines (links). 2D grid layout: Objects horizontally across the top; vertical lifelines representing time moving downwards.
Message Ordering Hierarchical decimal numbering on arrows along links (e.g., 1: submit(), 1.1: validate(), 1.2: save(), 2: notify()). Implicit top-to-bottom vertical progression of horizontal arrows between lifelines.
Object Lifetimes Object lifespans, activation focus bars, and destruction (×) are difficult to visualize. Clearly shown with vertical activation bars (focus of control) and explicit destruction markers.
Best Used For Evaluating object coupling, clustering of responsibilities, and architectural collaboration in a subsystem. Complex procedural logic, multi-step asynchronous flows, timeout/retry branches, and detailed timing analysis.
Viva Punchline: "Sequence diagrams highlight WHEN messages flow over time; Collaboration diagrams highlight WHO connects to whom in space with numbered message tags."
DIFF 3 Collaboration Diagram vs. Class Diagram (Teacher WhatsApp Question!)
Dimension Class Diagram (Static Model) Collaboration Diagram (Dynamic Model)
Model Type Static Structural Model: Shows the permanent structural skeleton of the system. Dynamic Behavioral Model: Shows runtime interaction for a specific use case scenario.
Represented Elements Class descriptors (types/blueprints), their attributes, methods, and generalized relationships. Specific runtime object instances (e.g., student: Student, c101: Complaint) and active links.
Time & Messages No messages, no time sequence, no execution flow. Only declarations of available operations. Numbered method calls passed across links during runtime execution of a particular transaction.

DIFF 5 State Machine Diagram vs. Activity Diagram
Dimension State Machine Diagram (Statechart) Activity Diagram
Focal Subject Entity-Centric: Tracks the lifecycle and status transitions of a single object (e.g., Complaint). Process/Workflow-Centric: Tracks multi-step business logic and data flow across multiple actors.

2. Task 1: Data & Class Design Viva Questions & Answers

Q1.1 What are the UML visibility specifiers, and why are attributes made private in design classes?

UML defines four visibility specifiers:

  • + Public: Accessible by any class anywhere in the system.
  • - Private: Accessible only within the declaring class itself.
  • # Protected: Accessible within the declaring class and its subclasses (generalization).
  • ~ Package / Default: Accessible by classes within the same package/module namespace.

Rationale for Private Attributes: Design classes strictly enforce Encapsulation and Information Hiding (David Parnas). If attributes like complaint.status were public, external controllers could arbitrarily mutate a complaint from SUBMITTED directly to RESOLVED, violating business invariants and skipping mandatory SLA and staff assignment rules. Private fields force all mutations through public validated operations (e.g., complaint.assignStaff(...)).

Q1.3 How is the User Generalization hierarchy structured in HCMS, and how is it persisted in relational SQLite?

UML Generalization Hierarchy: An abstract base class User contains common attributes: id: UUID, name: string, email: string, passwordHash: string, role: UserRole, phone: string, createdAt: timestamp.

Specialized subclasses inherit from User:

  • Student adds: rollNo: string, hostelBlock: string, roomNo: string.
  • HostelWardenAuthority adds: hostelAssigned: string, officeRoom: string.
  • MaintenanceStaff adds: category: SkillType (Electrical, Plumbing, Carpentry), activeTasksCount: int, isAvailable: boolean.
  • Administrator adds: adminLevel: int.

Relational Database Mapping Strategy: Relational databases do not have native inheritance. We utilize Single Table Inheritance (STI) with nullable specialized columns and a discriminator column (role):

CREATE TABLE users ( id TEXT PRIMARY KEY, name TEXT NOT NULL, email TEXT UNIQUE NOT NULL, password_hash TEXT NOT NULL, role TEXT CHECK(role IN ('STUDENT','WARDEN','STAFF','ADMIN')) NOT NULL, phone TEXT, roll_no TEXT, -- NULL for non-students hostel_block TEXT, -- Used for students and wardens room_no TEXT, -- NULL for staff/warden staff_category TEXT, -- NULL for non-staff is_available INTEGER DEFAULT 1, created_at DATETIME DEFAULT CURRENT_TIMESTAMP );

Why STI? Avoids expensive SQL JOIN operations on high-frequency login and token validation queries while ensuring single-point constraint validation.

Q1.4 How are multiplicities enforced in the Design Class Model and the SQLite database?
  • 1..1 Mandatory Single Association: Enforced in SQLite using NOT NULL on foreign key (e.g., student_id TEXT NOT NULL REFERENCES users(id)).
  • 0..1 Optional Association: Enforced via nullable foreign key column (e.g., assigned_staff_id TEXT REFERENCES users(id), which is NULL when complaint status is SUBMITTED).
  • 1..* Mandatory Collection: Enforced in application business logic within transactional boundaries (e.g., creating a complaint automatically inserts the initial AuditLogEntry with status SUBMITTED in the same database transaction).

3. Task 2: Architectural Design Viva Questions & Answers

Q2.1 Which architectural style is chosen for HCMS, and what is the technical justification?

Selected Style: 4-Layered Modular Monolith (Layered Architecture Style) structured into:

  1. Presentation Layer: React SPA (Vite) providing responsive UI components, client-side routing, and local state management.
  2. Routing & Security Layer: Express.js routing middleware, JWT authentication, and Role-Based Access Control (RBAC).
  3. Domain / Business Logic Layer: Core services implementing complaint lifecycle state machines, staff dispatching algorithms, and SLA breach calculations.
  4. Data Access & Persistence Layer: SQLite relational storage with connection pooling, transaction wrappers, and prepared SQL statements.

Justification:

  • Strict Separation of Concerns: UI components do not query the database directly; business validation rules are decoupled from HTTP transport.
  • Campus Scale Suitability: For a university campus of ~5,000 students and ~100 staff, a modular monolith handles the workload on a single modest server instance with sub-50ms response times.
  • ACID Transactional Guarantees: Updating a complaint status, reassigning staff, and writing an audit log requires atomic multi-table transactions, which are simple and robust in a single relational database.
Q2.2 Why NOT Microservices? What architectural trade-offs were considered?
Evaluation Factor Modular Monolith (Chosen) Microservices Architecture (Rejected)
Deployment Complexity Single deployable artifact; single Node.js runtime. Requires Docker containers, Kubernetes/orchestrator, service discovery, API gateways.
Data Consistency Atomic ACID transactions within SQLite. Distributed transactions, eventual consistency, complex two-phase commit or Saga patterns.
Network Latency In-memory function calls between layers (~0.01 ms). Inter-service HTTP/gRPC network hops and serialized JSON payloads (~10-50 ms).
Failure Modes Simple stack traces and centralized error logger. Cascading service failures, partial outages, distributed tracing overhead (Jaeger/Zipkin).
Viva Punchline: "Microservices solve organizational scaling problems for teams of hundreds of engineers. For HCMS, it introduces distributed systems fallacies without any tangible performance benefit."
Q2.3 How does SQLite handle concurrency when multiple students submit complaints simultaneously?

SQLite is often challenged in viva regarding concurrency. Here is the exact technical explanation:

  • WAL Mode (Write-Ahead Logging): We configure SQLite with PRAGMA journal_mode = WAL;. In WAL mode, readers do not block writers, and writers do not block readers. Multiple students can read complaints concurrently while a write occurs.
  • Node.js Single-Threaded Event Loop: Node.js processes HTTP requests asynchronously on a single event loop. When writing to SQLite via better-sqlite3, writes execute synchronously in microsecond bursts (~0.5 ms per insert).
  • Busy Timeout: SQLite is configured with PRAGMA busy_timeout = 5000;, ensuring that if two transactions attempt to commit at the exact same millisecond, the second transaction automatically retries for up to 5 seconds rather than throwing a lock error.

Q3.1 What is the difference between User Interface (UI) Design and Software Interface Design?
  • User Interface (UI) Design: The human-computer boundary. Focuses on visual affordance, ergonomics, wireframes, input validation messages, readability, and user flows (e.g., student filling a complaint lodging form).
  • Software Interface Design: The machine-machine or component-component boundary. Focuses on programmatic contracts, REST API endpoint schemas, data transfer formats (JSON), HTTP status codes, method signatures, and exception specifications.

5. Task 4: Component-Level Design Viva Questions & Answers

Q4.1 What is a Software Component, and what are Provided vs. Required Interfaces?

A Software Component is a modular, deployable, and replaceable part of a software system that encapsulates its implementation details and exposes behavior exclusively through declared interfaces.

  • Provided Interface (Lollipop notation –○): The services, APIs, and operations that the component implements and offers to external clients (e.g., IComplaintManagement provides submitComplaint(), getComplaintById()).
  • Required Interface (Socket notation –(): The services and dependencies that the component must consume from other components to fulfill its duties (e.g., ComplaintComponent requires INotificationService to send emails and IDataAccess to query SQLite).

6. Task 5: Design Consistency & Traceability Viva Questions & Answers

Q5.1 Walk the examiner through the complete Traceability Pipeline from SRS to Code.

The entire development sequence forms an unbreakable, verifiable traceability pipeline:

  1. SRS (Software Requirements Specification): Identifies Functional Requirements (e.g., FR-012: The system shall allow students to lodge hostel maintenance complaints).
  2. Use Case Model (Assignment 2): Groups functional requirements into formal Use Cases with boundaries and actors (e.g., UC-003: Submit Complaint).
  3. Scenarios & Activity Diagrams (Assignment 3): Models primary sunny-day workflows and exceptional branches (e.g., invalid input, duplicate complaint).
  4. Analysis Class Model (Assignment 4): Identifies problem-domain BCE objects (e.g., ComplaintFormUI, ComplaintController, ComplaintRecord).
  5. Collaboration & State Models (Assignment 5): Models dynamic object messaging and entity lifecycle states (SUBMITTED → ASSIGNED → IN_PROGRESS → RESOLVED → CLOSED).
  6. Design Class Model (Assignment 6, Task 1): Refines analysis classes into implementation types with private attributes, method signatures, return types, and SQLite foreign key constraints.
  7. Architectural Design (Assignment 6, Task 2): Partitions classes into 4 architectural layers (Presentation, Routing/Security, Domain Logic, Data Access).
  8. Interface Design (Assignment 7, Task 3): Details screen wireframes and REST API endpoints (POST /api/complaints).
  9. Component-Level Design (Assignment 7, Task 4): Defines component internal algorithms, preconditions, postconditions, and error handling pseudocode.
  10. Source Code & Test Cases: Implements the exact controllers, services, database tables, and automated unit tests.
Q5.2 What is Requirements Impact Analysis, and how does your design prevent regression?

Requirements Impact Analysis is the forward-tracing process executed when a customer requirement changes:

  • Scenario: Suppose the hostel administration introduces a new rule: "Carpentry complaints require prior inspection by the assistant warden before staff assignment."
  • Tracing Impact: Trace SRS Rule → UC-008 (Assign Complaint) → State Machine (add new state PENDING_INSPECTION) → Design Class (add assistantWardenId attribute to Complaint) → REST API (update PATCH /api/complaints/:id/assign validation) → StaffDispatchComponent (add inspection guard in pseudocode).
  • Benefit: Guarantees that modifications do not silently break other components or introduce undocumented behaviors.

7. Professor Curveball & Real Viva Questions (From WhatsApp & Past Exams)

Q7.1 What is a Guard Condition in UML diagrams? Show how you used it.

A Guard Condition is a boolean expression enclosed in square brackets [condition] placed on a transition in a state diagram or an interaction diagram. The transition fires only and only if the guard condition evaluates to TRUE at the exact moment the triggering event occurs.

Concrete HCMS Examples:

  • State Transition Guard: [staff.activeTasks < 5 && staff.isAvailable == true] / assignTask() — Prevents overloading a maintenance worker.
  • Resolution Guard: [inputOtp == complaint.verificationOtp] / markResolved() — Ensures worker cannot fake completion without the student's physical OTP verification.
Q7.2 What is the System Boundary of HCMS? What is inside vs. outside?

The System Boundary defines the exact perimeter of software components developed, deployed, and controlled within the HCMS project.

  • Inside Boundary: React frontend SPA, Express API controllers, Authentication middleware, Complaint state machine, Staff assignment logic, SQLite database, and Audit log records.
  • Outside Boundary (External Entities / Actors): Human users (Student, Warden, Staff, Admin), Campus LDAP/OAuth Authentication Server, Institute SMTP Mail Server, and Campus SMS Gateway.
Q7.3 Why must the Class Diagram be created before dynamic diagrams or code?

A dynamic interaction diagram (Sequence or Collaboration) models messages passed between objects. You cannot pass a message or invoke a method on an object unless that object's class has been defined with that specific operation signature and visibility in the Class Model. The class model establishes the fundamental structural vocabulary and static contracts without which dynamic behavior has no semantic basis.

Q7.4 Take any two classes, formulate a business rule, and explain the ambiguity if both classes try to enforce it. How do you resolve it? (Teacher WhatsApp Question!)

Selected Classes: Complaint and MaintenanceStaff.

Business Rule: "A maintenance staff member cannot be assigned more than 5 active complaints concurrently."

The Ambiguity / Problem:

  • If Complaint enforces it: complaint.assignTo(staff) checks staff.getActiveCount(). But Complaint should not manage staff workload policies — doing so increases coupling and leaks staff domain knowledge into the complaint entity.
  • If MaintenanceStaff enforces it: staff.acceptComplaint(complaint) checks this.activeTasks < 5. But what if two wardens assign tasks simultaneously? If both entities contain partial validation, responsibility is fragmented, creating duplication, race conditions, and maintenance nightmares.

Architectural Resolution: Apply the GRASP Information Expert pattern and introduce a Domain Service: StaffAssignmentService. This service queries the staff workload, acquires a lock on the staff record, verifies the invariant (activeTasks < 5), and atomically binds the staff member to the complaint within a single database transaction.

Q7.5 How is Fairness and Anti-Bias guaranteed in HCMS? (Teacher WhatsApp Question!)
  1. Deterministic FIFO Queueing: Unassigned complaints of identical priority are strictly ordered by created_at ASC. Wardens cannot arbitrarily favor one room over another.
  2. Automated SLA Escalation: If a normal complaint remains unassigned for >24 hours or in-progress for >48 hours, a background cron daemon automatically escalates the status to ESCALATED and alerts the Chief Warden.
  3. Load-Balanced Staff Allocation: The system automatically highlights the qualified staff member with the lowest current workload (least active tasks) to eliminate favoritism.
  4. Tamper-Proof Audit Logging: Every state change records the actor ID, previous status, new status, and timestamp. Wardens or staff cannot delete complaint histories without detection.
Q7.6 How do you validate the institutional email domain in code during login and registration? (Teacher WhatsApp Question!)

We enforce a strict two-stage validation strategy:

1. Strict Regex Pattern:

const LNMIIT_EMAIL_REGEX = /^[a-zA-Z0-9._%+-]+@lnmiit\.ac\.in$/; function validateInstitutionalEmail(email) { if (!email || typeof email !== 'string') return false; const cleanEmail = email.trim().toLowerCase(); return LNMIIT_EMAIL_REGEX.test(cleanEmail); }

2. Registration Verification Protocol:

  • Check database: SELECT id FROM users WHERE email = ? to prevent duplicate registrations.
  • Generate a cryptographically secure random token (crypto.randomBytes(32).toString('hex')) with a 15-minute expiration timestamp.
  • Dispatch an activation link via SMTP. The account remains in is_active = 0 status until the student clicks the link and sets their password.

Q7.8 Compare Software Process Models: Evolutionary Prototyping vs. Throwaway Prototyping. Why Evolutionary?
  • Throwaway Prototyping: A rapid, fragile mock-up (often hardcoded UI) created solely to clarify uncertain requirements, after which the prototype is completely discarded and development begins from scratch.
  • Evolutionary Prototyping (Our Choice): An initial, well-architected core system is constructed with solid design patterns (clean layers, modular classes). Each sprint refines, hardens, and extends the exact same codebase from prototype into production software.
  • Why Evolutionary for HCMS? Our core requirements were already formalized in Assignments 1-5 (SRS baseline). Throwing away code would waste time; evolutionary prototyping allowed our Assignments 6 & 7 design models to directly become the final functioning application.

UML Unified Modeling Language — standard visual specification language for object-oriented software engineering (OMG standard).
Analysis vs. Design Class Analysis class = Conceptual domain entity (BCE stereotypes). Design class = Implementation-ready blueprint with types, visibility, and DB mapping.
GRASP General Responsibility Assignment Software Patterns (Information Expert, Creator, Controller, Low Coupling, High Cohesion).
SOLID Principles Single Responsibility, Open/Closed, Liskov Substitution, Interface Segregation, Dependency Inversion.
Aggregation vs. Composition Aggregation = Weak "has-a", independent lifecycles (Hostel ♦–> Staff). Composition = Strong "part-of", shared lifecycle (Complaint ⧫–> AuditLog).
Provided vs. Required Interface Provided (Lollipop –○) = Services a component offers to others. Required (Socket –() = Services a component needs from others.
SQLite WAL Mode Write-Ahead Logging: enables concurrent readers without locking writers; maximizes local throughput.
Guard Condition Boolean condition [condition] that must evaluate to true before a state transition or message can execute.
Traceability Matrix A cross-reference table proving every requirement (FR) maps to a Use Case, Class, Component, REST endpoint, and Test Case.
SLA (Service Level Agreement) Time bound within which a complaint must be resolved (e.g., Electrical Emergency = 4 hours, General Carpentry = 48 hours).
